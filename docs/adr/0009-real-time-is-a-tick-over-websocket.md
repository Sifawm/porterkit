# Real time is a Tick on the server over WebSocket; an unreliable channel waits for a Game that needs it

Porter serves a Game that runs in real time with what it already had plus one thing: the Tick, a fixed advance of the Match that Porter asks of the Manager at the rate the Game definition declares. The Manager holds the rules and the whole state, as in any other Game; clients send what their User asks for and receive what happened and where things are, as Game messages over the same connection. The protocol, the two transports, the client and the Bindings did not change. The alternative we were asked for was to turn the transports into installable packages and add one over WebRTC.

We chose the Tick because the Game behind the request, a Bomberman on a grid, was not held back by the transport. What it lacked was a server that advances without a message arriving. Its state changes little each Tick and tolerates a late message, so a reliable ordered channel carries it. A Game with no `tickRate` is untouched, which is how the Games Porter was made for keep working as they did.

We left the transports where they are because publishing `Sink` and `Link` would freeze the wrong seam. Both are one channel, reliable and in order. A channel that drops and reorders, over WebRTC or WebTransport, is a second one beside the first: it is signalled through it, it carries only what the next Tick replaces, and the rule that a second connection replaces the first has to be written again for a User with two. That design needs a Game to prove it, as a generic room needed an integrator that was not a Game ([ADR 0002](0002-porter-knows-games.md)).

The cost is that Porter is not for a Game where tens of milliseconds decide: a shooter, a fighting game. Such a Game asks for more than a channel: prediction with reconciliation, which needs numbered client messages, and the server rewinding its state to judge a shot. We take it up when an Integrator has that Game and has measured, under the packet loss its Users really have, that WebSocket stalls where its interpolation cannot hide it. An Integrator pays meanwhile for interpolation and prediction on its own, in the code that draws, and installs `ws` even when every client of its uses SSE.
