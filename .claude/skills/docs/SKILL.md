# Docs

`apps/docs` is the Starlight site for Integrators: how to use Porter, not how it is built. It documents exactly what Porter v1 does. The specification in `docs/spec/` stays the normative source; the site is written from it and from the code, never the other way round.

## 1. Find the pages a change touches

Every page lists what it covers in its frontmatter, as paths from the repository root with the GitHub anchor of a heading:

```yaml
spec:
  - docs/spec/nestjs.md#ticks
  - CONTEXT.md
```

For each spec section, ADR or file you changed, find its pages:

```sh
rg -l 'docs/spec/nestjs.md#ticks' apps/docs/src/content/docs
```

Search for the file without the anchor too: a page that cites `docs/spec/protocol.md` whole covers every section of it. A renamed heading changes its anchor; update every `spec:` entry that used it.

## 2. Update them

- Say what Porter does for the Integrator, in the second person where it helps. Rewrite the spec; do not paste it.
- Only what is built and specified. No roadmap, no "coming soon", and nothing from a spec's "Verify during construction" stated as fact.
- Use the vocabulary of `CONTEXT.md`, with its capitals (User, Match, Manager, Applier…).
- When a section of the spec has no page, add it to the page whose folder fits, or create a page:

  | Folder                           | Holds                                                                      |
  | -------------------------------- | -------------------------------------------------------------------------- |
  | `start/`                         | Installation and the first steps on server and client                      |
  | `guides/game/`                   | Games map, Game definition, settings, Profile                              |
  | `guides/manager/`                | The Manager: context, Match hooks, messages, timers, Ticks, memory, errors |
  | `guides/client/`                 | `createPorter`, Appliers, transports, connection                           |
  | `guides/react/`, `guides/godot/` | The Bindings                                                               |
  | `guides/rooms/`                  | Login and Token, the Admin, room control                                   |
  | `guides/testing/`                | Testing a front                                                            |
  | `concepts/`                      | Glossary, room lifecycle, who does what                                    |
  | `reference/`                     | Configuration, protocol, rejections                                        |

  A new page has `title`, `description`, `sidebar.order` and `spec` in its frontmatter.

- `concepts/glossary.md` follows `CONTEXT.md` entry by entry. `concepts/who-does-what.md` follows "Who does what" and "Out of v1" in `docs/spec/README.md`.

## 3. Code

- Code that uses Porter's API is a real file in `apps/docs/src/snippets/`, compiled by the `typecheck` target. A page shows a part of it between `// #region name` and `// #endregion`:

  ```mdx
  import { Code } from '@astrojs/starlight/components';
  import { snippet } from '../../../../snippet';
  import manager from '../../../../snippets/misfit/manager.ts?raw';

  <Code code={snippet(manager, 'hooks')} lang="ts" title="misfit.manager.ts" />
  ```

  `snippet(source)` without a region shows the whole file. A snippet can also be a file of `examples/`, imported the same way.

- Inline code blocks only for shell commands, JSON configuration, GDScript and the shapes of the wire.
- `snippets/testing/*.test.ts` run under Vitest in the `test` target.

## 4. Links

Internal links are absolute and carry the base: `/porterkit/guides/manager/ticks/`, with the trailing slash, and `#anchor` when it points at a heading. `starlight-links-validator` fails the build on a link or anchor that does not exist; relative links are refused.

## 5. The API reference

`reference/api/` is generated by `starlight-typedoc` from the five packages on every build and is not versioned. Do not edit it. Its text is the TSDoc of `packages/*/src` and each package's `README.md`; change those instead, in the same commit as the code.

## 6. Humanizer, last

When the prose is final, run the `humanizer:humanizer` skill in file mode on every page you changed, and on any TSDoc comment you wrote or changed. It edits prose only and leaves code, frontmatter and link targets alone. A page that sells keeps to facts: the landing states an advantage as what Porter does, with its number when there is one.

## 7. Check

```sh
pnpm exec oxfmt apps/docs
pnpm exec nx run-many -t typecheck build test -p @porterkit/docs
```

The build regenerates the API reference and validates every link. Commit the pages with the change they document, as `docs(docs): …` when the change is only to the site.
